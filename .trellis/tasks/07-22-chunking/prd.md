# Chunk transcript into time-bounded segments

## Goal

Turn a transcribed episode's word-level WhisperX output (`episode.transcript_data`) into `chunk` rows — cleaned text + embedding + `start`/`end` timestamps — so retrieval and jump-to-timestamp playback have something to query. This is the `indexing` (+ `cleaning`) module per spec.md §5, and closes spec.md's M1 milestone ("先定死 chunk 表结构，跑通单集全链路").

## Confirmed Facts (from code)

- `episode.transcript_data` (JSONB) already stores the raw WhisperX aligned result after transcription: `{model, language, segments: [{text, start, end, words: [{word, start, end}, ...]}, ...]}` (source: [transcriber.py:33-54](backend/src/rag_podcast/transcription/transcriber.py#L33-L54), persisted as-is at [worker.py:129](backend/src/rag_podcast/transcription/worker.py#L129)).
- The `chunk` table already exists and matches spec.md §4.2 exactly: `id, episode_id, podcast_id, text, embedding(Vector(1024)), start, end, speaker(nullable)` ([models/chunk.py](backend/src/rag_podcast/models/chunk.py)). No migration needed for the table itself.
- `indexing/`, `cleaning/`, `retrieval/`, `qa/` packages all exist but are **empty stubs** — nothing implemented in any of them yet. `chunk` table is empty even for episodes with `transcript_status = done`.
- Embedding provider is already decided and configured in `.env`: **DeepInfra**, model `BAAI/bge-m3`, `EMBEDDING_BASE_URL=https://api.deepinfra.com/v1/openai` (OpenAI-compatible client). Resolves spec.md §7 open Q1 — just wire a client using existing `settings.embedding_*`.
- No diarization step exists in the transcription pipeline (WhisperX result has no `speaker` key) — `chunk.speaker` stays `NULL` for every chunk, matching spec.md §4.2's "reserved field, MVP leaves unfilled" assumption.
- Established codebase precedent for async background work (transcription): a status enum column (`transcript_status`) + poll-and-claim worker loop, crash-safe via a startup reset of stale `PROCESSING` rows ([worker.py:23-43](backend/src/rag_podcast/transcription/worker.py#L23-L43)), driven by a thin CLI ([cli.py](backend/src/rag_podcast/transcription/cli.py)) run manually on the host (`uv run python -m rag_podcast.transcription.cli`) — not wired into `docker-compose.yml`. This task follows the same shape.
- Migration precedent for adding a status enum column: [0002_episode_ingestion_fields.py](backend/alembic/versions/0002_episode_ingestion_fields.py).
- **Bug found during planning**: `whisperx.align()` returns only `{"segments": ..., "word_segments": ...}` (confirmed in installed source, [alignment.py:418](backend/.venv/Lib/site-packages/whisperx/alignment.py#L418) — no `language` key). [transcriber.py:120-144](backend/src/rag_podcast/transcription/transcriber.py#L120-L144) reads `result["language"]` from the pre-align `model.transcribe()` output only to pick an alignment model, then overwrites `result` with `whisperx.align()`'s return value — silently dropping `language` before it ever reaches `episode.transcript_data`. The `Transcriber` Protocol docstring's example return shape (which shows a top-level `"language"` key) does not match what the real code produces. Confirmed with user: fix this inline in this task, since indexing needs language as an input (e.g. language-aware cleaning) anyway.
- The 2 currently-transcribed episodes have no language captured (lost to the bug above) and cannot recover it without re-running transcription — the raw pre-align result was never persisted.
- **Real data check (episode 1's actual `transcript_data`, queried from the dev DB)**: this podcast is Chinese mixed with English (e.g. segment text `"Hello 大家好,欢迎来到我的播客节目..."`). Its `words` array is **character-level for CJK content**, not word-level: the first three entries are `{"word":"H"}`, `{"word":"e"}`, `{"word":"l"}` (splitting "Hello" into single letters) — WhisperX's alignment model aligns per-character for this language, unlike space-delimited languages. Segment 1 alone is 17.3s — under the 20s min-duration floor — confirming chunks routinely need to merge 2+ segments to clear the minimum (validates the greedy-accumulation algorithm below).
- **Re-investigation trigger (2026-07-27, user)**: pure wall-clock duration bounds ignore that speakers talk at different speeds, so a 20–90s window can hold wildly different amounts of actual content. Measured on the real test episode (`aligned_test.json`, 121 segments, 510s total): per-segment WhisperX word-entry density ranges **0.90 to 5.55 entries/sec** (min/p25/median/p75/max = 0.90 / 2.64 / 3.15 / 3.51 / 5.55) — a ~6x spread. This directly confirms the concern: two chunks of equal duration can carry very different amounts of semantic content, which plausibly hurts embedding/retrieval consistency (spec.md §7 Q3 already flagged duration bounds as an unvalidated `[假设]`, deferred to M4 tuning — this reopens that assumption itself, not just its numeric values).
- **Punctuation is present in the word list with its own timestamp — but its shape is script-dependent** (verified 2026-07-27 against real project data, not just the CJK-word-splitting fact above): in the actual bilingual episode (`aligned_segments.txt`), punctuation is a **standalone word entry** (e.g. `{"word": ",", "start": 6.195, "end": 6.275}` — 3 lone commas in segment 0 alone), consistent with WhisperX's character-level CJK alignment. In the English-only sample (`aligned_test.json`), punctuation is instead **fused onto the preceding word** (`"ways,"`, `"manufacturing."`) — never standalone. Any punctuation-based logic must handle both shapes (`word == ","` or `word.endswith((",", "."))`), the same script-shape gotcha already hit for text-joining and word-counting. Also verified: `clean_words` ([filler_words.py:20-26](backend/src/rag_podcast/cleaning/filler_words.py#L20-L26)) safely passes punctuation tokens through unfiltered either way — `_normalize` strips ASCII `string.punctuation` before the filler-set comparison (a lone `","` normalizes to `""`, not a filler word), and CJK punctuation isn't in `string.punctuation` at all — so no cleaning bug here, but the standalone-token shape is a free, previously-unused signal for chunk-boundary detection (see Requirements).
- **Word-count is not a safe drop-in replacement metric**: because WhisperX aligns CJK content **character-by-character** (see above), `len(segment["words"])` is not comparable across scripts — one Chinese character and one English word both count as "1", but carry very different amounts of information. Any content-based bounding metric must either be robust to this (e.g. count on `chunk.text` characters instead of word entries) or explicitly solve it (e.g. a real subword tokenizer). This is the same class of script-awareness gotcha already solved once for text joining (see `cleaning/text_join.py`'s `join_words`), now resurfacing for chunk-size measurement.
- **Re-reversed 2026-08-12 (user)**: an earlier draft of this task had `chunk.text` as the *original, uncleaned* transcript (per spec.md §4.2's `原始转录片段`), with cleaning happening per-chunk, after chunking, only to build a throwaway string for the embed call. That's been overridden: cleaning now runs once, upfront, on the whole transcript, *before* chunking — the chunker's input is already-cleaned segments (matches `BaseChunkerInterface.py`'s `Chunker` Protocol docstring, "Input: Cleaned WhisperX segments", written during implementation). Consequence: `chunk.text` is now the **cleaned** text (filler words removed) — the same text used for storage, display/jump-to-audio, and embedding; there's no longer a separate original-vs-cleaned split, and no per-chunk ephemeral string. This intentionally drops the older goal of displayed text matching the literal spoken audio word-for-word (filler words included) — accepted trade for a simpler single-pipeline-stage design.
- The character-level CJK join bug (naive `" ".join(...)`-ing surviving Chinese characters produces `"H e l l o 大 家 好"`, a space wrongly inserted between every character) is real but lives entirely inside `clean_words` itself (`cleaning/filler_words.py`, its own per-language `joined_by` join), which already handles it — not something the chunker or embedder need to guard against separately now that they only ever see post-cleaning text.

## Requirements

**Transcription bug fix** (`transcription/`)
- `LocalWhisperX._transcribe_sync` must preserve the language detected by `model.transcribe()` (before alignment overwrites `result`) and return it alongside `segments`/`word_segments` — e.g. capture `language = transcribe_result["language"]` before calling `whisperx.align()`, then merge it back into the dict returned to the worker.
- Add `episode.language` (nullable string) column via migration; `transcribe_episode` in `transcription/worker.py` sets it alongside `transcript_data`/`transcript_status` when a transcription completes.

**Cleaning** (`cleaning/`) — not this task's deliverable
- `clean_words(segments, language=None)` and `join_words(words, language=None)` are implemented and owned by the separate, already-archived `07-28-filler-word-cleaning` task (its own PRD has the actual requirements/design). This task only *consumes* their existing signatures — but it does own the **orchestration**: the worker calls `clean_words` exactly once per episode, on the full `segments` list, *before* calling `chunker.build_chunks(...)` (see Architecture in design.md). `join_words` is still used inside the chunker's oversized-segment pre-pass (see Chunking below), to rebuild the text of a synthetic segment — not by the embedder anymore. No cleaning behavior itself is (re)specified here.

**Chunking** (`indexing/`) — two-phase plan, decided 2026-07-27 (see "Chunking Strategy Decision & Roadmap" below for full rationale)

*Shared contract (both phases)*
- Chunking is implemented as a **swappable boundary strategy behind one stable output contract**: every strategy is a function `(segments: list[dict], **strategy_params) -> list[ChunkSpan]`. `ChunkSpan` (`text`, `start`, `end`, `segments`) does not change between strategies and carries no information about which strategy produced it. **Revised 2026-07-29**: the fourth field is `segments` (segment-shaped dicts spanned by the chunk), not a flattened `words` list as first drafted — word-level timestamps are needed to derive `ChunkSpan.start`/`.end` and to drive the oversized-segment split fallback (see design.md's "`ChunkSpan.segments`, not `.words`" note).
- Downstream code (`indexing/embedder.py`, `indexing/store.py`, `indexing/worker.py`) consumes only `list[ChunkSpan]` and must contain **zero branching on which chunking strategy ran** — swapping strategies is a config/call-site change in the worker only, never a downstream code change.
- Every chunk is one contiguous time span (`start`→`end`, no gaps skipped over) — never assemble a chunk from non-adjacent spans (spec.md §4.4 iron law). Holds for every strategy, not just Phase 1.
- `ChunkSpan.start`/`.end` are **recomputed per chunk from word-level timestamps**, not copied from a spanned segment's own `start`/`end` field: `start` = the first included word's own `start`, `end` = the last included word's own `end` (derived by drilling into `chunk.segments[*]["words"]`; see design.md's `SizeBasedChunker` algorithm step 5). WhisperX's segment-level boundary can include silence padding beyond the actual first/last spoken word, so a chunk assembled from whole segments must not just reuse `chunk.segments[0]["start"]`/`chunk.segments[-1]["end"]` directly. Persisted into `chunk.start`/`chunk.end` (see Persistence below) — this is the actual value stored, not the raw segment boundary. Holds for every strategy.
- The chunker's *input* `segments` are already cleaned — the worker calls `clean_words` once on the whole transcript before `chunker.build_chunks(...)` (see "Cleaning" above). `ChunkSpan.text` = concatenation of the (cleaned) `text` field of every segment included in the chunk. Never rebuilt from a word list — see the "Re-reversed 2026-08-12" note in Confirmed Facts. Holds for every strategy.

*Phase 1 — size-based (ships first, fixes the confirmed speech-rate bug)*
- Bound chunks primarily by **BGE-M3 subword token count of `chunk.text`** (configurable min/max), not wall-clock duration and not raw character count — directly targets the measured 6x word-density variance (see Confirmed Facts), and unlike character count, stays script-neutral across this podcast's actual code-switching passages (whole English-language segments, e.g. a briefly-interviewed foreign speaker — not just isolated loanwords). **Revised 2026-07-27**: character count was considered first and rejected — English needs ~5 chars/word vs. Chinese's ~1–2 chars per comparable unit of meaning, so a fixed char budget would systematically under-fill chunks landing on English passages relative to Chinese ones, reintroducing the exact uneven-content bug this phase exists to fix, just along a language axis instead of a speech-rate axis. Subword tokenization is what a multilingual tokenizer is specifically trained to normalize across scripts, so it doesn't have this failure mode.
- Load BGE-M3's tokenizer only (not the model) via the lightweight HuggingFace `tokenizers` package — no torch, no model weights, just its vocab/`tokenizer.json`. This is a new dependency, accepted deliberately: lighter than what spec.md §3's "no heavy ML dependency" reasoning was guarding against (local model weights + CUDA), and ties naturally to BGE-M3's own 8192-token input ceiling. Loading/caching mechanics decided during planning — see design.md's "BGE-M3 tokenizer loading & caching" section. `backend/scripts/tokenizer_playground.py` (added during planning, 2026-07-29) implements this same loading approach standalone — tokenize an ad-hoc `--text` string, or get per-segment token-count/density stats over a real WhisperX transcript JSON (`--transcript`, defaults to `en_aligned_test.json`) — used to pin the tier numbers below and available for further spot-checking as real episodes get indexed.
- **Token thresholds vary by episode length (decided 2026-07-29, user)**: a single flat token budget doesn't fit this podcast catalog's actual genre spread — a 5–10min news-style episode plausibly packs much more content per minute than a 60–120min talk/interview episode (e.g. Acquired), so a fixed budget would over-fragment dense short episodes or under-fragment sparse long ones. Modeled as a small number of **discrete duration tiers** (not a continuous proportional formula — there's no eval data yet, spec.md M4 doesn't exist, to justify fitting a curve; a lookup table is honest about being a provisional guess and easier to spot-check per tier later). Each tier is `(min_tokens, max_tokens, desired_tokens)` — see the greedy-target stopping rule below for what `desired_tokens` is used for; it defaults to the tier's `(min_tokens + max_tokens) / 2` but must be independently **tunable** (overridable per tier), not hardcoded to the midpoint.
  **Pinned 2026-07-29 `[assumption]`** (via `backend/scripts/tokenizer_playground.py` against real data — see below):
  | Tier | Episode duration | min_tokens | desired_tokens | max_tokens |
  |------|------|------|------|------|
  | Short (news-style) | ≤ 15 min | 100 | 175 | 250 |
  | Medium (standard talk/interview) | 15–45 min | 150 | 275 | 400 |
  | Long (deep-dive, e.g. Acquired) | > 45 min | 250 | 425 | 600 |

  Grounded in a real measurement, not a blind guess: `tokenizer_playground.py` run against `en_aligned_test.json` (a real 426-segment, 32.4min English episode) measured **~248.5 tokens/min** overall (8,056 tokens / 1945.4s) — which is why the Medium tier (this episode falls in it) is anchored at `max_tokens=400`, close to what the old 90s duration bound already implied in token terms for a typical-paced episode. Short/Long tiers are extrapolated from the Medium anchor (~0.6x / ~1.5x) per the user's "proportional to episode duration" framing — **not** independently measured against real short-news or real long-form-interview audio (none exists in this repo yet); revisit once real episodes of those genres are actually indexed. Tier boundaries (15min/45min cutoffs) are similarly a reasoned guess, not measured.
  **Single set of thresholds across languages, not split by language (re-checked 2026-07-30, user question)**: a real Chinese episode (`aligned_test.json`, 47 segments, 17.3min — episode 1's actual transcript, spec.md's own test data) measured only **~186.3 tokens/min**, ~25% below the English sample above, which on its face looked like a script-driven gap. But that comparison is confounded — two different shows, different speakers, different topics, different pacing, not a controlled test of the *tokenizer's* per-language efficiency. A controlled test — 3 genuinely translation-equivalent sentence pairs (same meaning, both languages) tokenized via `tokenizer_playground.py` — came back **39 tokens English vs. 39 tokens Chinese, exactly equal in total**, with per-pair ratios (1.18x, 0.81x, 1.08x) scattered around 1.0 with no systematic bias toward either language. That confirms the ~25% aggregate gap is a speaking-pace/genre artifact of those two specific episodes (which the duration-tier axis already exists to absorb), not evidence that BGE-M3 needs more tokens per unit of *meaning* in one script than the other. So: **no separate per-language token thresholds** — a single tier table serves both languages (and this podcast's actual code-switched mix of the two), consistent with the original rationale for choosing subword tokenization over character count in the first place.
- **Greedy nearest-target stopping rule (decided 2026-07-29, user, inspired by a chunking-strategy article the user supplied)**: within the "legal" zone — both mins already cleared, neither max yet breached — the chunker no longer always extends as far as possible before being forced to stop by a max bound. Instead, at each candidate segment boundary it compares the error-to-target (`|desired_tokens − current_token_count|`) against the error-to-target one segment further ahead (`|desired_tokens − token_count_including_next_segment|`); if the current candidate is already closer to `desired_tokens` than the next one would be, it closes here. This works as a cheap one-step lookahead (not a full scan) because cumulative token count only grows as segments are added, so the error is V-shaped (strictly decreasing, then strictly increasing) — the first point where "one more segment gets worse, not better" *is* the local optimum, no exhaustive search needed. Scoped to **tokens only**, not duration — duration keeps its purely hard-bound (OR-max/AND-min) role from the bound-gating logic above, no target/lookahead of its own. Hard bounds still take precedence: this rule only decides *where within the legal window* to stop, it never overrides the OR-max/AND-min gate itself.
- **Duration bounds stay flat, not tiered, but widened (decided 2026-07-29, user)**: unlike token thresholds, wall-clock duration bounds remain a single pair across all episodes — tiering them the same way would add complexity with no clear benefit, since duration is now a secondary/safety-net bound rather than the primary content-size signal. **Pinned `[assumption]`: `chunk_max_duration_seconds = 360.0`** (up from `90.0`, a 4x widening) — sized so even a long-form episode running well below the real sample's measured ~248.5 tokens/min (e.g. half that rate, a genuinely slow, sparse talker) can still reach the Long tier's `max_tokens=600` ceiling (~290s at half-rate) with headroom to spare, without duration_max cutting it off first. `chunk_min_duration_seconds` is unaffected (`20.0`).
- **Bound-gating logic (decided 2026-07-29, user)**: closing a chunk buffer requires **OR** on the max side (either token-max *or* duration-max being exceeded triggers a close attempt — token-max is expected to be the one that actually fires in practice given the widened duration bound, but duration-max independently still catches a low-density stretch that runs too long without ever hitting a token ceiling) and **AND** on the min side (**both** token-min and duration-min must already be cleared before a close is allowed — token-min alone isn't sufficient, since a token-dense-but-very-short chunk is still a choppy listening experience; duration-min keeps its independent veto even though token count is the dominant signal on the max side).
- Token counts are computed per segment and summed for the running buffer check (cheap, O(n) over the episode) rather than re-tokenizing the full growing buffer text on every segment (O(n²), not worth the marginal precision — a subword tokenizer's merge behavior can differ by at most a token or two at a segment boundary when tokenizing joined vs. separate text, negligible against a token budget in the hundreds).
- **Oversized-single-segment trigger stays duration-only (decided 2026-07-29, user)**: `_split_oversized_segment`'s trigger condition (a single segment's own duration exceeding `max_duration`) does not get an added token check. BGE-M3's 8192-token input ceiling gives enormous headroom over the "budget in the hundreds" range these thresholds live in, so a token-dense-but-short single segment isn't a real overflow risk worth defending against. When that duration-triggered split does happen, prefer splitting at **sentence-final punctuation** within that segment's word list over an arbitrary word-count cutoff — punctuation timestamps are already present in the data (see Confirmed Facts; handle both the CJK standalone-token and Latin fused-onto-word shapes), a free precision improvement over the current implementation's plain word-count split, not a new dependency.
  - **Revised 2026-08-21 (user)** — the decision above stands unchanged (duration-only trigger, sentence-final punctuation preferred), but the mechanism it described has been replaced, so read `_split_oversized_segment` as `_split_long_segments` / `_split_segment` / `_cut_index`. The split is now a **pre-pass** over the whole segment list before the accumulation loop, not an in-loop fallback emitting finished `ChunkSpan`s, and it cuts into `ceil(duration / max_duration)` **roughly equal shares** rather than greedy max-width windows. Two reasons: greedy windowing left a remainder (361s against a 360s bound gave 360s + 1s), and because the old fallback emitted finished chunks while the buffer restarted at the following segment, that remainder could never merge with anything — it stood as its own chunk. As a pre-pass the pieces are ordinary segments, so they re-enter the gate above and an end piece falling under the mins merges with its neighbour. Punctuation preference survives as a *snap* applied to each equal-share boundary; the contrast is now "equal share vs. equal share nudged to a sentence end", not "punctuation vs. word-count". Design detail in design.md's "Oversized-segment pre-pass" section.
  - **Consequence worth stating explicitly**: pieces are **not** guaranteed to fall under `max_duration`. Word granularity is the floor — a single 400s word cannot be split — so the bound is best-effort by construction, and the accumulation loop is expected to tolerate an over-max segment without special-casing it.
- Exact token-count thresholds (per tier) are a calibration detail, not a blocking decision — ship with reasonable provisional defaults (marked `[assumption]` in config, same convention spec.md uses) and adjust from spot-checking output, same as the original flat duration bounds were.
- **Pipeline ordering (revised 2026-08-12, user)**: filler-word cleaning (`clean_words`) now runs *before* chunking, once, on the whole transcript — not an either-order choice. Boundary detection (segment/punctuation-based) always scans the cleaned word list; this loses no sentence-boundary signal since cleaning never strips punctuation tokens (verified above). The fixed invariant is `ChunkSpan.text` always being assembled from the (cleaned) per-segment `text` fields, never rebuilt from any word list — see the "Re-reversed 2026-08-12" fact above.

*Phase 2 — embedding-similarity-biased cut selection (planned follow-up, not blocking Phase 1)*
- Within the same Phase-1 min/max bounds, bias *which* candidate segment boundary a chunk closes at toward the point of highest embedding distance between adjacent units, instead of Phase 1's own nearest-token-target criterion (see the greedy nearest-target stopping rule above). Bounds remain a hard outer constraint in both phases — Phase 2 only substitutes a different in-range boundary-selection criterion (embedding distance instead of token-target distance), same one-step-lookahead shape.
- Boundary-detection embeddings are computed via the existing hosted embedding API pattern (`indexing/embedder.py`'s HTTP client), optionally a cheaper/smaller hosted model than BGE-M3 since these vectors are ephemeral (used only for distance comparison, never persisted) — this does not reopen spec.md §3's hosted-only architecture decision. A **local** model would reopen that decision and is explicitly not part of this plan.
- Must still return `list[ChunkSpan]` — see Shared contract above. No downstream consumer should need to know Phase 2 ran instead of Phase 1.
- Known open gaps, non-blocking (tracked, not resolved): the similarity threshold has no eval harness (spec.md M4) to validate against yet, so Phase 2's quality can't be quantitatively measured until M4 exists — built now anyway per user decision, revisit threshold/validation once M4 lands.
- **Comparison-unit granularity — likely resolved by punctuation, not a new dependency**: WhisperX segments run a 3.8s median (some are single-word fragments), too fine-grained to embed and compare directly. Since punctuation timestamps are already present in the data (see Confirmed Facts), the comparison unit can be **punctuation-delimited sentences** (grouping words across segment boundaries where needed) rather than raw segments or an arbitrary window — a standard unit for embedding-based semantic chunking in the literature, available here for free.

**Embedding** (`indexing/`)
- Call the DeepInfra BGE-M3 endpoint (OpenAI-compatible embeddings API) via `settings.embedding_*`, once per chunk, embedding **`ChunkSpan.text` directly** — no separate ephemeral string, since cleaning already ran on the whole transcript before chunking (see Cleaning/Chunking above). Store the resulting 1024-dim vector in `chunk.embedding`.
- The script-aware join (no space adjacent to a CJK character, single space between Latin-script tokens) happens once, inside `clean_words`, when segment `text` is rebuilt during cleaning — not a separate concern for the embedder. A naive uniform-space join is confirmed broken on this project's real (Chinese-language) data — see Confirmed Facts.
- Chunk-then-embed (independent per-chunk pooled vectors), not late chunking — see Out of Scope.

**Full-text search** (`indexing/`)
- Add a `tsvector` column (generated or populated at insert time) on `chunk`, derived from `chunk.text`, with a GIN index — storage for future BM25/hybrid search. This task only produces and stores the column; querying/ranking with it is retrieval's job (see Out of Scope).

**Persistence** (`indexing/`)
- Write one `chunk` row per chunk: `episode_id`, `podcast_id` (denormalized from the episode's podcast), `text` (cleaned — see Chunking above), `embedding` (computed directly from `text` — see Embedding above), `search_vector` (tsvector, generated from `text`), `start`, `end`, `speaker=NULL`.
- Re-running indexing for an episode must not accumulate duplicate chunks: delete that episode's existing chunk rows before inserting the new set. This also makes re-indexing with different chunk parameters (spec.md M4 tuning) safe to re-run.

**Orchestration**
- Add `episode.index_status` enum column (`PENDING/PROCESSING/DONE/FAILED`), default `PENDING`, and `episode.language` (nullable string), via a new Alembic migration — `index_status` mirrors `transcript_status`.
- New `indexing` worker mirrors `transcription/worker.py`: reset stale `PROCESSING` rows on startup, poll for `transcript_status = DONE AND index_status = PENDING`, claim atomically, run clean → chunk → embed → persist, then mark `DONE`/`FAILED`.
- New thin CLI (`rag_podcast.indexing.cli`, invoked via `uv run python -m rag_podcast.indexing.cli`) wires config → worker, following `transcription/cli.py`'s shape. Unlike transcription this needs no GPU/extra — safe to eventually run in the `api` container, but wiring into `docker-compose.yml` is not required for this task (transcription's worker isn't wired in either).

## Acceptance Criteria

- [ ] Given an episode with `transcript_status = DONE`, running the indexing worker produces `chunk` rows whose `start`/`end` respect the configured BGE-M3 token-count bounds (Phase 1) and secondary duration bounds, with no overlap and no gaps within a chunk.
- [ ] Spot-check on a mixed-language passage (e.g. an English-language segment inside the Chinese episode) confirms chunk sizes stay comparable in actual content/information to Chinese-only chunks — not just comparable in token count by construction, but plausible on a manual read.
- [ ] `indexing/embedder.py`, `indexing/store.py`, and `indexing/worker.py` contain no conditional logic branching on which chunking strategy (Phase 1 vs Phase 2) produced a given `ChunkSpan` — verified by inspection, since only one strategy needs to actually ship for this task's own completion.
- [ ] `chunk.text` has filler words removed — confirmed by comparing a stored chunk's `text` against `clean_words()`'s output for its source segments (cleaning applied once, before chunking).
- [ ] `clean_words` correctly removes filler words and preserves surviving words' timestamps, and its script-aware join does not insert spaces between CJK characters (already covered by `test_cleaning.py`) — since the chunker's input segments (and therefore `chunk.text`) are already cleaned, no separate embedder-side join/regression test is needed.
- [ ] Manual spot-check of 3 chunks against the actual audio: `start`/`end` line up with spoken content within ±2 seconds (spec.md M1 bar).
- [ ] Every stored chunk has a 1024-dim `embedding` populated from the DeepInfra BGE-M3 API.
- [ ] `chunk.episode_id` / `chunk.podcast_id` are correct; `chunk.speaker` is `NULL`.
- [ ] Killing the indexing worker mid-episode and restarting it resumes cleanly: `index_status` resets `PROCESSING → PENDING` on startup, and re-processing the episode replaces rather than duplicates its chunk rows.
- [ ] Chunk size bounds and overlap are read from settings/config, not hardcoded.
- [ ] Every stored chunk has a populated `search_vector` (tsvector) derived from its text, covered by a GIN index.

## Chunking Strategy Decision & Roadmap

Reopened 2026-07-27 (see "Re-investigation trigger" fact above), resolved same day after reviewing user-supplied research (`podcast_chunking_strategies.md`) against this project's actual constraints. Full candidate comparison, for reference:

- **`chunk.text` character count (rejected 2026-07-27)** — zero new dependencies, fixes the same-language speech-rate variance, but **not** script-neutral enough for this podcast: it has real code-switching passages (whole English segments, e.g. a briefly-interviewed foreign speaker), not just isolated loanwords. English needs ~5 chars/word vs. Chinese's ~1–2 chars per comparable unit of meaning, so a fixed char budget under-fills English-passage chunks relative to Chinese ones — reintroducing the uneven-content bug along a language axis. Initially chosen as the near-term fix, then superseded once this failure mode was identified as a real (not just residual) risk for this specific podcast.
- **Real subword token count via BGE-M3's own tokenizer (chosen for Phase 1)** — most accurate/language-neutral (subword tokenization is what a multilingual tokenizer is trained to normalize across scripts), aligns naturally with BGE-M3's 8192-token input ceiling. Adds a new dependency (HuggingFace `tokenizers`, loading only BGE-M3's vocab/`tokenizer.json` — no torch, no model weights), which is a real but light cost against spec.md §3's "keep the repo free of heavy/extra ML dependencies" reasoning (that reasoning was about local model weights + CUDA, not a small tokenizer-only package) — accepted as the right trade once character count's language-axis failure mode was confirmed.
- **TextTiling (lexical cohesion)** — cheap (no API calls), but needs a CJK segmenter (e.g. jieba) to produce comparable word units on this bilingual transcript — same class of script gotcha already hit for text-joining and word-counting. Also targets topic-drift, a different (unconfirmed) failure mode from the measured size-variance bug, and the literature (including the user's own research doc) flags lexical cohesion as the weak baseline specifically on casual multi-party spoken transcripts. Not chosen for Phase 1; not ruled out long-term.
- **Embedding-similarity-biased cut selection (chosen for Phase 2)** — script-agnostic for free (BGE-M3 is multilingual by design), reuses the existing hosted embedding API with no new dependency. Targets topic-drift rather than the measured size-variance bug, so it's additive to Phase 1's bounds, not a replacement. Chosen as the Phase 2 follow-up specifically because it's the semantic option with the smallest architectural footprint.
- **LumberChunker (LLM-in-the-loop segmentation)** — reuses the existing LLM API (no new dependency) but means dozens of LLM calls per 40–90 min episode purely for boundary decisions, stacking a new per-episode cost center on top of spec.md §7's already-flagged transcription-cost risk; benchmarked on clean written narrative (books), a bigger genre gap from conversational ASR transcript than any other candidate. Not chosen.
- **Local embedding model for Phase 2's boundary detection** — considered and explicitly rejected: even a "small" local model reopens spec.md §3's and §7 Q7's deliberate decision to keep embedding hosted-only, regardless of model size. Phase 2 uses a hosted model only (possibly a cheaper one than BGE-M3, since Phase 2's detection vectors are never persisted and are therefore exempt from the "embedding model can't change mid-corpus" lock-in rule — see Confirmed Facts).

**Decision**: ship Phase 1 (BGE-M3 token-count bounds, duration as secondary UX bound) now; build Phase 2 (embedding-similarity-biased cut selection) as a second implementation of the same `list[ChunkSpan]` contract, without waiting for spec.md M4's retrieval-eval harness to exist first (explicit user call — Phase 2's quality can't be quantitatively validated until M4 lands, but the interface is built now so it's a drop-in swap once that measurement becomes available).

## Out of Scope

- **Query-time retrieval strategy** (single-episode full-context vs. multi-episode RAG routing) — user's idea: if a question is scoped to one episode, skip RAG and feed the full transcript into the LLM prompt directly (long context windows make this viable); only run chunk retrieval when a question spans multiple episodes of the same podcast. This is a `qa`/`retrieval`-module decision (spec.md M2), not `indexing`. Recorded here as a design note for that future task — chunking still has to happen regardless, since multi-episode questions still need chunk rows in pgvector.
  **Why this matters (user's rationale, 2026-07-25)**: with modern long-context LLMs, single-episode Q&A doesn't need RAG at all — the whole transcript fits in the prompt. That means RAG's actual value in this project is narrower and sharper than "answer questions about a podcast": it's specifically *cross-episode* semantic search — finding the right moment across many episodes without the user knowing which one it's in. This should be the framing the future qa/retrieval task's PRD opens with, not an afterthought; it also means that task's eval/quality bar should weight multi-episode queries more heavily than single-episode ones, since single-episode is the "easy," non-differentiating case.
- **Late chunking** — considered and rejected for now. Late chunking needs token-level embeddings (embed the whole document once, mean-pool per chunk afterward) so chunk vectors stay aware of the surrounding document. DeepInfra's BGE-M3 endpoint is the standard OpenAI-compatible `/embeddings` shape — one pooled vector per input, no token-level output. Getting token-level output would require either Jina's API (the only provider found with a native `late_chunking` param) or self-hosting BGE-M3 — both reopen spec.md §3's already-made decision to keep embedding on a hosted API specifically to avoid a second local-GPU dependency. Confirmed with user: skip for now; revisit only if that embedding-hosting decision itself gets revisited.
- **BM25/hybrid-search querying** — this task stores the `tsvector` column (see Requirements) but does not implement ranking, RRF-merging with dense results, or any retrieval-time logic. That belongs to the future `qa`/`retrieval` task alongside the RAG-routing decision above.
- Batch/multi-episode indexing at scale; **quantitative** chunk-size/strategy tuning via a retrieval eval harness (spec.md M3/M4) — this task targets the single-episode M1 bar and ships Phase 2 (see Chunking Strategy Decision & Roadmap) without that harness, on a qualitative/spot-check basis only; the worker design supports batch naturally but is only validated here against the currently-transcribed episodes.
- Wiring the indexing worker into `docker-compose.yml` — run manually on the host for now, matching the transcription worker's current setup.
